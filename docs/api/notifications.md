# Notification System API (Phase 15)

## Overview

The Notification System provides in-app notifications for users (students, sponsors, admins) in the ClassPay application. Notifications represent actionable or informational messages generated by backend services (such as payment confirmations, class enrolments, and payment reminders).

Push notifications (FCM/APNs), email delivery, WhatsApp, Telegram, and scheduled reminder workers are deferred to future delivery phases.

---

## Notification Types

Notification types are centralized in `App\Services\Notification\NotificationType`:

| Type Constant         | String Value          | Purpose                             |
| --------------------- | --------------------- | ----------------------------------- |
| `PAYMENT_REMINDER`    | `payment.reminder`    | Upcoming payment due reminder       |
| `PAYMENT_SUCCESS`     | `payment.success`     | Payment successfully completed      |
| `PAYMENT_FAILED`      | `payment.failed`      | Payment attempt failed or rejected  |
| `PAYMENT_OVERDUE`     | `payment.overdue`     | Payment schedule overdue alert      |
| `PAYMENT_PENDING`     | `payment.pending`     | Payment pending manual verification |
| `CLASS_ADDED`         | `class.added`         | Student enrolled in a new class     |
| `CLASS_REMOVED`       | `class.removed`       | Student removed from a class        |
| `SYSTEM_NOTIFICATION` | `system.notification` | General system alert                |

---

## API Endpoints

All endpoints require `Authorization: Bearer {token}` (`auth:sanctum`). Users can strictly only view, mark as read, or manage their own notifications.

| Method | Endpoint                                      | Purpose                                                         |
| ------ | --------------------------------------------- | --------------------------------------------------------------- |
| `GET`  | `/api/v1/notifications`                       | List authenticated user's notifications (paginated, filterable) |
| `GET`  | `/api/v1/notifications/unread-count`          | Get total count of unread notifications for authenticated user  |
| `GET`  | `/api/v1/notifications/{notification}`        | View single notification details                                |
| `POST` | `/api/v1/notifications/{notification}/read`   | Mark a notification as read (idempotent)                        |
| `POST` | `/api/v1/notifications/{notification}/unread` | Mark a notification as unread (idempotent)                      |
| `POST` | `/api/v1/notifications/read-all`              | Mark all notifications for authenticated user as read           |

---

## Query Parameters (`GET /api/v1/notifications`)

- `page` (int, default `1`) — Page number.
- `per_page` (int, default `20`, max `100`) — Number of records per page.
- `unread` (boolean/string, `true`/`1`) — Filter only unread notifications (`read_at IS NULL`).
- `type` (string) — Filter by specific notification type (e.g. `payment.reminder`).

Notifications are ordered newest first (`created_at DESC`).

---

## Authorization & Security

- Requests are authenticated via `auth:sanctum`.
- Scoped strictly to `$request->user()->appNotifications()`.
- Accessing or modifying another user's notification returns `403 Forbidden`.
- Standard error envelope is returned for validation (`422`), authentication (`401`), and authorization (`403`) failures.

## Notification Templates & Placeholder Substitution

Backend notifications can be rendered dynamically from active database templates in `notification_templates`:

### Example Template Record

- `notification_type`: `payment.reminder`
- `subject`: `"Payment Reminder for {{class_name}}"`
- `body`: `"Dear student, your payment of RM{{amount}} for {{class_name}} is due on {{due_date}}."`
- `status`: `"active"`

### Placeholder Substitutions

Template placeholders use `{{variable_name}}` syntax:

- `{{amount}}`
- `{{class_name}}`
- `{{due_date}}`
- `{{organization_name}}`
- `{{payment_url}}`

Rendering is safe and non-executable (`preg_replace_callback`). If a template placeholder is missing from passed variables, the placeholder is left intact or handled safely without raising exceptions. If no database template is active for a given type, `NotificationService` falls back to standard default message formatting.

---

## Related Records

Notifications reference related domain models using polymorphic relationship fields:

- `related_type` (e.g. `App\Models\Payment`, `App\Models\PaymentSchedule`, `App\Models\ClassModel`)
- `related_id` (bigint ID of the referenced model)

Eloquent MorphTo relationship `Notification::related()` allows automatic resolution of the associated record.

                "created_at": "2026-09-12T10:00:00.000000Z"

            "current_page": 1,
